# ADR 0015: Sequelize for the application database

On 2026-10-16 the application database moved from Prisma 7 to Sequelize 6, because the project's brief requires Sequelize. Only the application database changed. Customer databases are still reached with plain `pg` through the executor (ADR 0010), and never through an ORM.

**Libraries.** `sequelize` 6.37.8, `sequelize-typescript` 2.1.6 for decorator models (`@Table`, `@Column`), `@nestjs/sequelize` 12 for the Nest connection, and `sequelize-cli` 6.6.5 for migrations. The user chose decorator models and the Nest module over plain `Model.init`, because they read like the rest of the NestJS code. Sequelize 7 is still in alpha. `sequelize-typescript` has had no release since November 2023; it works with Sequelize 6.37 and the Nest module requires it, but it is the first thing to look at if a Sequelize upgrade breaks.

**Layout.** In `packages/database`, each kind of thing is in its own folder and each table in its own file: `src/enums/` (`PlanTier`, `ConnectionStatus`, `SslMode`, `QueryKind`, `QueryStatus`), `src/types/` (`<Table>Attributes` for a row, `<Table>CreationAttributes` for what creating one needs), `src/models/` (one `@Table` class per table), `src/create-sequelize.ts` (connection settings shared by the app, scripts, and tests), `migrations/`, `config/database.cjs`, and `.sequelizerc`. In `@ayd/core`, `src/database/database.module.ts` and `database.service.ts` replace `PrismaModule` and `PrismaService`. The repositories keep their interfaces and are renamed `Prisma…` to `Sequelize…`, so services and controllers did not change.

**Layout changed 2026-10-18.** The three folders above made one table three folders to read, and every enum belongs to exactly one table. Each table now has its own folder, `src/tables/<name>/`, holding `<name>.model.ts`, `<name>.types.ts`, and its enums (for example `tables/connection/` has `connection-status.enum.ts` and `ssl-mode.enum.ts`), behind an `index.ts`. `src/tables/index.ts` re-exports every folder and keeps the `models` list. The exported names did not change, so no importer of `@ayd/database` changed.

**Enums as constant objects.** Each enum is `const X = { … } as const` with a type of the same name, not a TypeScript `enum`. Code can write `ConnectionStatus.Active`, and code that already passed the string `'active'` still type-checks. Typing the model columns with them found a value the first search missed: connections can also be `'failing'`.

**The migrations own the tables.** The models only describe them for queries: `synchronize: false` and `autoLoadModels: false`, so `@nestjs/sequelize` never calls `sync()`. Every `@Column` names its type, because the worker's dev runner (tsx) does not emit the decorator metadata `sequelize-typescript` would otherwise guess it from. `packages/database` compiles with `useDefineForClassFields: false`; with ES2022 class fields, a declared model property hides the getter Sequelize defines, and every value reads `undefined`.

**Migrations rewritten in JavaScript.** The user chose sequelize-cli migrations (`queryInterface`) over keeping Prisma's SQL files. The six files from `20261009180000-auth.cjs` to `20261014170000-usage-counters.cjs` rebuild Prisma's tables with the same column types and constraint and index names; a schema-only `pg_dump` of a database they built and of the Prisma-built development database were identical (160 lines). Each `up` runs in one transaction. `npm run migrate --workspace=@ayd/database` (`scripts/migrate.cjs`) first adopts a Prisma-built database: when `_prisma_migrations` exists and `SequelizeMeta` does not, it records each finished Prisma migration under the name of the file that replaces it, in one transaction, and stops on a Prisma migration it does not know. `_prisma_migrations` is left in place.

**Time zones.** Prisma read `TIMESTAMP` (without time zone) as UTC. Sequelize parses only `TIMESTAMPTZ` itself; a `TIMESTAMP` value falls through to `pg`, which reads it as the machine's local time, so on a machine in India every time, token expiry included, would move by 5 h 30 min. Migration `20261016120000-timestamps-with-time-zone.cjs` changes the 18 time columns to `TIMESTAMPTZ(3)` with `AT TIME ZONE 'UTC'`, which keeps each stored instant. On a copy of the development database the row counts and the sum of every instant were the same before and after. Setting a global `pg` type parser instead was rejected: it would also change how customer query results are read. `database.int-spec.ts` writes an instant and reads it back.

**Query patterns that differ from Prisma.**

- A transaction is `db.transaction(async (transaction) => …)`, and every query inside must be given `{ transaction }`; one without it runs outside the transaction and is not rolled back.
- The connection lock is `findOne({ lock: transaction.LOCK.UPDATE, transaction })` instead of raw `SELECT … FOR UPDATE`.
- `Model.update` returns `[rowsChanged]` and `Model.destroy` returns a count; refresh-token rotation checks the first is exactly 1.
- Usage counters add with raw `INSERT … ON CONFLICT DO UPDATE SET questions = usage_counters.questions + EXCLUDED.questions`, because Sequelize's `upsert` can only overwrite. Postgres does the adding, so jobs finishing together all count (tested with 20 at once).
- The proposal cache upserts with `bulkCreate` and `updateOnDuplicate`, which updates only the listed columns, so an entry keeps its id, hits, and creation time, as with Prisma. A hit is `hits + 1` in SQL.
- A connection update drops `undefined` keys from the patch first: Prisma skipped them, Sequelize would write `NULL`.
- Ownership through a relation (`connection: { userId }` in Prisma) is an `include` of `Connection` with `required: true`.

**Behaviour that changed.** A history record written again for a retried job now also refreshes `finished_at`. Deleting an account that no longer exists does nothing instead of throwing, as the in-memory test repository already did. Transactions have no time limit; Prisma stopped them after a timeout, which the schema refresh had raised to 30 s.

**Not adopted.** `@InjectModel` and `SequelizeModule.forFeature` in every module: the repositories use the static models (`User.findOne`), which Sequelize binds to the one connection `DatabaseModule` creates, and take `DatabaseService` only for transactions and raw SQL. That keeps the constructors as they were and lets integration tests build a repository with `new SequelizeAuthRepository(openAppDatabase())`.
