# ADR 0014: The web app

Phase 9 adds the React frontend in `apps/web`, an npm workspace like the others (ADR 0001).

**Stack.** React 19 and TypeScript, bundled by Vite, as the blueprint fixes (section 4). Mantine is the component library, the user's choice: complete, accessible components as packages, with no CSS framework to learn alongside, and a chart package built on Recharts, which the blueprint names. TanStack Query holds server data (loading, errors, caching, refetching after a change); React Router handles pages. Unit tests use Vitest and Testing Library in jsdom, beside the source as `*.spec.ts(x)` (ADR 0005). Vitest runs on Vite's own config, so the app and its tests transform code the same way; Jest would need a second set of transforms for TSX and CSS imports. Browser end-to-end tests (Playwright) stay planned for `e2e/` at the repo root.

**One origin.** The browser talks only to the web server, which passes `/v1` to the API: Vite's dev proxy locally, and one domain in front of both in production (Phase 12). The httpOnly refresh cookie, scoped to `/v1/auth`, then works without CORS, and no credentials cross origins. The API still has no CORS or CSRF configuration; both belong to Phase 10, before the app and API are ever served from different origins.

**Tokens.** The access token (15 minutes) lives only in memory, in the `AuthProvider`, so a script injected into the page cannot read it from storage, and a reload restores it from the refresh cookie through `POST /v1/auth/refresh`. The API client adds it to each request and, on a 401, refreshes once and repeats the request; auth routes are never repeated. The API treats a refresh token presented twice as stolen and revokes the whole sign-in, so the client never runs two refreshes at once: callers in a tab share one pending refresh, and tabs take turns through the browser's Web Locks API.

**Google sign-in from a browser.** `GET /v1/auth/google/start` and `GET /v1/auth/google/callback` are visited by the browser itself, not called with fetch, so they answer with redirects instead of JSON: the callback sets the refresh cookie and sends the browser to `APP_WEB_ORIGIN`, and a known failure on either route goes to `/sign-in?error=<code>`. Unexpected errors still reach the error filter and are logged. Dev login stays a JSON route; the sign-in page shows it only in development builds.

**Following jobs.** Work that opens a user database is a worker job (ADR 0011), so the app follows it live through `GET /v1/jobs/:id/events`. The stream is read with fetch and a stream reader, because `EventSource` cannot send the `Authorization` header and the API refuses a token in the URL. When the stream ends before the job does (the server closes it after 10 minutes, or the network drops), `watchJob` reconnects up to three times, after 0.5, 1, and 2 seconds; if those fail as well, it polls `GET /v1/jobs/:id` every 1.5 seconds. A stream that delivered an event resets the count. A stream that stays open but sends nothing for 45 seconds, not even the 15-second keep-alive, is treated as dead and reconnected: a server restart behind a proxy can leave the browser's side open forever. A 4xx (the job expired, or the user is signed out) stops it. Leaving the page aborts it.

**Answers.** The ask screen draws the chart the server chose (ADR 0012) and never picks one itself, so the same result always looks the same. Rows arrive as arrays in column order, and PostgreSQL sends bigint and numeric values as strings, so the chart and the table's sorting convert them. The results table draws only the visible rows once there are more than 100 (TanStack Virtual), and the chart code, most of the app's size, loads only when an answer has a chart. Each failure code the user can act on has its own title; the message under it is the API's.

**Accessibility.** Browser tests run axe on every page at desktop and phone sizes. They found Mantine's default contrast too low in light mode, so `src/app/theme.ts` uses blue 8 for primary buttons, gray 7 for dimmed text, and a darker text shade on light badges, buttons, and alerts; scrollable code blocks are focusable so a keyboard can scroll them.

**Code layout (2026-10-16).** `src/` is grouped by feature, so a reader can follow a request from a button to the URL it calls:

- `app/` starts the app: `main.tsx` (loaded by `index.html`), `providers.tsx`, `router.tsx` (which URL shows which page), `AppLayout.tsx`, and `theme.ts`.
- `lib/` is the plumbing every feature shares, with no screens: the API client (`api-client.ts`), following jobs (`jobs.ts`), the response types (`api-types.ts`), the query cache (`query-client.ts`), and every cache key (`query-keys.ts`).
- `components/` holds UI used by more than one feature (`ErrorAlert`, `JobProgress`).
- `features/<name>/` holds one area of the app: `auth`, `account`, `connections`, `ask`, `history`, and `usage`. Each has an `api.ts` with every request its screens make (reads as TanStack Query hooks, changes as plain functions that take the API client), its pages, a `components/` folder when it has its own pieces, and an `index.ts` that lists what other folders may import. Code outside a feature imports only from its `index.ts`.

Every `/v1` URL the app calls is in a feature's `api.ts`, except the job routes, which all features use, in `lib/jobs.ts`. The cache keys are in one file rather than per feature because one screen's change refreshes another screen's data (asking refreshes history and usage); per-feature keys would make features import each other in a circle. The response types stay in one file too, because they are copied from the server as one set and may later be generated from the OpenAPI document. Not adopted from common feature-folder templates: axios (the fetch client already adds the token and refreshes it), a global store such as Zustand (server data lives in TanStack Query, and the only other shared state is the session, in React context), and Tailwind (Mantine styles the app).

**Types.** The response types in `apps/web/src/lib/api-types.ts` are copied from the server code rather than imported, because the server types live in Node-only packages (`@ayd/core`) the browser bundle must not include. The error codes come from `@ayd/shared` as a type-only import. Moving the response types into `@ayd/shared` is a later clean-up; until then a route change must update both.

**Module format.** The web app is the one ES-module workspace. It does not extend `tsconfig.base.json`, which targets Node with CommonJS output; `tsc` only type-checks it and Vite builds it.
