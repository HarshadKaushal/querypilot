# ADR 0012: Model layer

Phase 7 turns questions into SQL with a language model. This records how the platform talks to models; the ask pipeline that uses them is built on top.

**Provider.** Gemini through Google AI Studio keys, as locked in the blueprint. The primary model is `gemini-3.8-flash` and the fallback `gemini-3.5-flash-lite`: the two models Google's documentation recommends for new projects in October 2026, both stable, both on the free tier. Preview models are avoided (stricter limits, shorter life), and the 2.5 family is limited to existing users. The models are settings (`LLM_PRIMARY_MODEL`, `LLM_FALLBACK_MODEL`), so changing them needs no code.

**API.** Google's official SDK, `@google/genai`, calling the Interactions API, which Google recommends for new projects (`generateContent` remains supported). Each call sends a system instruction, the prompt, and `response_format` with `mime_type: application/json` and a JSON Schema. `store: false` keeps interactions stateless on Google's side; no conversation state is kept between calls. Temperature is 0, so the same question over the same schema gives the same SQL. The SDK's own retries are off: the fallback chain decides what to try next.

**One schema per answer.** Each answer shape is a Zod schema. `z.toJSONSchema` turns it into the JSON Schema sent to the model, and the same Zod schema validates the answer. A model cannot return a field the code does not expect.

**Fallback chain.** `LlmClient` tries the providers in order. A rate limit (429), an outage (5xx, timeout, network), or an answer that is not valid JSON in the expected shape moves on to the next model. A missing or refused key (401, 403) and a cancelled job stop at once, because the next model would fail the same way. A 400 or 404 (an unknown model name, a schema the model cannot follow) counts as a bad answer and also falls back. Every attempt is recorded with its model, outcome, latency, and token counts, for the accounting step.

**Errors.** Provider error text can echo the request, so it is never kept or shown: each failure gets a fixed sentence, classified from the HTTP status.

**Where it runs.** Only in the worker, from jobs; the API never imports `LlmModule`. The key is `GEMINI_API_KEY`, optional so the worker still starts without it, and model calls then fail as "not configured". Compose passes it to the worker from the root `.env`. Log redaction covers `*.apiKey`.

**Data leaving the platform.** Free-tier keys let Google use prompts and answers to improve its products. Prompts carry only the allowlisted schema and the question. Result rows go to the model only when the connection's `sendSampleRowsToLlm` setting allows it (user's decision, Phase 7). Production should use a paid key; the deployment phase records this.

**Ask pipeline (step 2).** `POST /v1/connections/:id/questions` queues a `question.ask` job. The worker's `AskJobRunner` reads the allowlisted schema (only allowed tables and columns, with descriptions and keys), asks for `{status, sql, assumptions, clarifyingQuestion, explanation}`, and stops at `ambiguous` or `unanswerable` before anything runs. The SQL goes through the guard; a rejection goes back to the model with the guard's reason, at most twice. PostgreSQL's `QUERY_INVALID` gets one more attempt, with fixed feedback, never the database's text. Timeouts, permission errors, and connection problems are not retried. The system prompt states the guard's rules and lists its allowed functions, so a first answer usually passes; the question is wrapped in `<question>` tags and declared data. A schema larger than 24,000 characters of prompt is cut to the tables that share the most words with the question, plus the tables their foreign keys point to (blueprint 9.3). Model failures become `LLM_NOT_CONFIGURED` (no key) or `LLM_UNAVAILABLE` (every model failed or answered malformed JSON). The result carries every model attempt for the accounting step.

**Proposal cache and self-healing (step 3).** A proposal that passed the guard and ran is stored in `query_cache`, keyed by the connection, the allowlisted schema's fingerprint, and a SHA-256 of the normalized question (lowercased, spaces collapsed, trailing punctuation dropped); never rows. The fingerprint changes with every refresh and allowlist edit, so old entries stop matching, and saving a new entry drops the connection's entries for older fingerprints. A cached proposal skips the model but still goes through the guard and the executor; one the guard now rejects, or that PostgreSQL rejects as invalid, is dropped and the model is asked. Ambiguous, unanswerable, and failed answers are not cached. When a query fails with `QUERY_SCHEMA_CHANGED`, the worker refreshes the schema and answers once more against the new snapshot; tables and columns the refresh finds are new and stay hidden until the owner allows them, so healing never widens what the model sees. A second failure, or a failed refresh, is returned as it is. The result says `cached` and `schemaRefreshed`.

**Chart, summary, and accounting (step 4).** An answered question also gets:

- `chart`: chosen by fixed rules from column types and row counts, no model (blueprint 9.8). One number is a stat card; a date then numbers, a line, thinned to 200 points keeping the first and last; one label and one non-negative number over 2 to 5 rows, a pie; one label and numbers up to 50 rows, bars; anything else, the table.
- `facts`: computed by the server: row count, truncation, min, max, total, and average per number column, and, only when the connection allows rows, the top 5 items for a label and a number (labels are row values; ADR 0013).
- `summary`: a second model call with the question and the facts, plus up to 20 rows only when the connection's `sendSampleRowsToLlm` is on (user's rule). Every number in the model's summary must appear in the facts, the rows it was shown, or the question, exactly or rounded; otherwise, or when the call fails, a template built from the facts is used (`source: template`). A summary never fails the answer. Summaries go to a lighter model first (`LLM_SUMMARY_MODEL`, default `gemini-3.5-flash-lite`), then the primary: a summary is short and its numbers are checked, so the lighter model answers faster and draws on its own rate-limit quota, leaving the primary's for SQL. Token counts barely differ between models; the gain is time and quota. An empty setting sends summaries through the main chain.
- `usage`: model calls, input and output tokens, model time, query time, total time, the models that answered, and whether a fallback was needed (blueprint 9.10). Phase 8 stores these in history.

**Tests.** No test calls a real model (`docs/testing.md`). `FakeLlmProvider` in `@ayd/core/testing` answers from a script and records what it was shown. `npm run try-llm --workspace=@ayd/worker` checks a real key by hand.

**Scripted model for browser tests.** With `LLM_FAKE=true`, the worker's model chains hold only `ScriptedLlmProvider`, which answers by fixed rules on the question's words (a count, a count per region, an ambiguous "best", a DELETE for the guard to refuse, otherwise unanswerable) and writes a summary without numbers. It exists so the browser tests run the real pipeline after the model without calling one. The settings check refuses it in production, as it refuses `SSRF_ALLOW_PRIVATE`.
