# ADR 0011: Jobs and the queue

Work that reaches a user database runs as a job in the worker, not inside an HTTP request (ADR 0003). The API adds the job and answers at once with its id; the client reads the outcome from `GET /v1/jobs/:id`. It can follow the job live over Server-Sent Events and cancel it (step 4). One user cannot crowd out the others (step 5).

**Queue.** BullMQ 6 on the existing Redis, one queue (`JOB_QUEUE_NAME`, default `ayd-jobs`) for every kind of job. The job name is its kind. The kinds are `query.run` (step 3a) and `connection.create`, `connection.update`, `connection.test`, and `schema.refresh` (step 3b), so only the worker connects to user databases. Job ids are random UUIDs, never BullMQ's counters. The queue name is a setting so that tests, and environments that share a Redis, use their own.

**Ownership.** Every payload names its owner. `JobQueue.get(id, userId)` returns NOT_FOUND for a malformed id, a missing job, and someone else's job alike, as every other read does.

**Outcomes, not exceptions.** A runner returns `{ ok: true, result }` or `{ ok: false, error }`, where the error is a stable code from `@ayd/shared`, a message written in this codebase, and a `retryable` flag. A guard rejection is `SQL_REJECTED` with the guard's reason and code. An executor failure keeps its code. An `AppException` thrown on the way (NOT_FOUND, SCHEMA_NOT_READY) becomes an outcome. Only an unexpected error escapes, so BullMQ marks the job failed, the worker logs it through `safeErrorDetail`, and the owner sees `INTERNAL_ERROR` with a fixed sentence. No driver or library text reaches a client.

**What a query job does.** The worker loads the latest snapshot and allowlist, runs the SQL guard, resolves the connection (ownership, decrypting the credentials in memory, pinning the address through the SSRF guard), and runs the guard's SQL through the executor. Phase 7 puts the model in front of the guard; the rest stays.

**New and changed connections.** The API validates the input (400 when it is bad) and seals the credentials with the platform key; the job carries only the sealed form. The worker opens them in memory, pins the host, and runs the read-only check, and stores the connection, or the change, only if the check passes. A login that can write is never stored, as before the queue. `PATCH` answers 200 for a change that cannot reach another database or login (label, sample-rows setting) and 202 with a job otherwise. Once a job has run, the worker rewrites its stored payload without the sealed credentials, so the finished job kept for the result TTL holds none. A job that throws keeps them for its retry; once it has no attempts left, they are removed too.

**Where results live.** In Redis, as the job's return value, for `JOB_RESULT_TTL_SECONDS` (15 minutes by default); BullMQ removes finished jobs after that. The result holds at most the row cap and 5 MB. Nothing about the job is written to Postgres yet. The `queries` history table, which never holds rows, comes with Phase 8, where the blueprint specifies it.

**States.** The owner sees `queued` (BullMQ's waiting, delayed, prioritized), `running` (active), `succeeded` (completed with an ok outcome), `failed` (completed with an error outcome, or given up by BullMQ), or `cancelled` (completed with `JOB_CANCELLED`). A running job carries its `stage`: `checking_sql`, `connecting`, and `running_query` for a query; `checking_access` for connection jobs; `reading_schema` for a refresh. A job whose owner asked to cancel it carries `cancelRequested: true` until it ends.

**Progress stream (step 4).** `GET /v1/jobs/:id/events` is Server-Sent Events. It sends a `job` event with the full view each time the job changes and ends after a finished state. Each API process opens one BullMQ `QueueEvents` stream and fans events out by job id; a listener re-reads the job rather than trust the event. A re-read every 2 seconds catches anything the event stream missed, a comment line every 15 seconds keeps proxies from closing the connection, and the stream ends after 10 minutes. The first read happens before any header is sent, so a missing or foreign job is a normal 404. Authentication is the `Authorization` header, so the client uses fetch-based SSE; a token in the URL would be written to access logs, which rules out the browser's `EventSource`. Polling `GET /v1/jobs/:id` remains the fallback.

**Cancellation (step 4).** `POST /v1/jobs/:id/cancel` sets a Redis key for the job (a day) and publishes its id on a channel. A worker that reaches a cancelled waiting job ends it at once without running it. Every worker subscribes to the channel, and the one running the job aborts its BullMQ signal; runners check it between stages, the executor before connecting, while waiting for a slot, and between batches of rows. A statement already running is not interrupted: it finishes or hits the statement timeout. Each stage also re-checks the key, for a request that arrived before the worker registered the job. The outcome is `JOB_CANCELLED`, which is not retried. A cancelled create or update stores nothing. Cancelling a finished job returns it unchanged (200).

**Retries and the dead-letter set (step 4).** Only a crash is retried: a runner that throws, or a worker that dies, whose job BullMQ finds stalled when its lock expires and runs again. Expected failures are outcomes and are never retried. A job gets `JOB_ATTEMPTS` runs (3) with exponential backoff from one second. One with none left stays in BullMQ's failed set for `JOB_FAILED_RETENTION_SECONDS` (7 days) for inspection, with its sealed credentials removed; the owner sees `INTERNAL_ERROR`. Every job is safe to run twice: queries and tests are read-only, a refresh adds a version, an update applies the same change, and a create carries an id the API chose, so a retry that finds its row returns it instead of storing a second one.

**Fair scheduling and per-user caps (step 5).** BullMQ's per-group fairness is a BullMQ Pro feature, so the open-source queue gets two rules instead. First, a user may have `JOB_MAX_ACTIVE_PER_USER` unfinished jobs (3), queued or running, across every API and worker process: the API claims a slot in a Redis sorted set before queueing, a further job is refused with `TOO_MANY_JOBS` (429), and the worker releases the slot when the job completes, is cancelled, or is given up. A slot is a one-hour lease, so one whose release was lost frees itself. Second, the slot's number is the job's BullMQ priority (lower runs first), so each user's first job goes ahead of anyone's second, and seconds ahead of thirds; equal priorities keep their order. A heavy user's jobs therefore wait at most behind one job from each other user per round, and never fill the queue.

**Logs.** The worker logs each finished job with its id, kind, outcome code, and duration. It never logs the SQL, which can hold customer values, or any result rows.

**Code layout.** The queue, the runners, and the services they need (connections, schema, the SQL check) live in `@ayd/core`, so the worker never imports the API. The API keeps the HTTP controllers. Core's `startJobWorker` takes jobs from BullMQ, subscribes to cancellations, and hands each job to `JobProcessor`; the worker app runs it and logs what it reports. Workers run `WORKER_CONCURRENCY` jobs at once (5 by default); the per-connection Redis slots from ADR 0010 still limit how many reach one database.
