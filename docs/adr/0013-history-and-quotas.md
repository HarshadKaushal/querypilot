# ADR 0013: Query history and quotas

Phase 8 keeps a record of what each user asked and limits how much they can ask.

**History (step 8a).** The `queries` table holds one row per finished `question.ask` or `query.run` job, keyed by the job id: the question or SQL, the SQL that ran (as the guard rewrote it), the status (`answered`, `ambiguous`, `unanswerable`, `failed`, `cancelled`), the error code, row count, truncation, schema version, whether the answer came from the cache, the summary, the models, tokens, and timings. It has no column for result rows (an integration test checks the table's columns), so history never holds rows. The worker's `JobProcessor` writes the entry when a job finishes, including cancellations, and a job given up after its last crash is recorded as failed. A failed write is logged and never fails the job; a retried job writes the same id again.

**Reading history.** `GET /v1/history` lists the owner's entries newest first, 20 by default and 50 at most, with keyset pagination: the cursor is the last entry's time and id, and the next page reads entries older than it, so pages stay fast and do not shift when new entries arrive. `GET /v1/history/:id` shows one entry. `DELETE` removes one or all. Every read and delete is filtered by the owner; another user's id is NOT_FOUND. Entries go with their connection or account.

**Re-run.** `POST /v1/history/:id/rerun` replays the stored SQL as a new `query.run` job (the user's choice): fresh rows, no model call. The worker runs it through the guard again, so a schema or allowlist change since then is caught. An entry with no SQL (ambiguous, unanswerable, failed before SQL ran) cannot be re-run.

**Summaries and row values.** History keeps the summary, so the summary must not carry row values the owner did not allow out. When the connection's `sendSampleRowsToLlm` is off, the facts behind the summary hold only column names, the row count, and numeric totals, minimums, and maximums; the labelled top items, which are row values, are left out, so neither the summary model, the template, nor history sees them (fixed in step 8a after the history test found a label in a template summary).

**Rate limit (step 8b).** A user may submit `SUBMISSIONS_PER_MINUTE` (10) pieces of work a minute: questions, SQL, and history re-runs share the allowance. Past it the API answers 429 `RATE_LIMITED` with a `Retry-After` header in seconds. The count is a sliding window in Redis (a sorted set of hit times, trimmed and checked in one Lua script using Redis's own clock), so it holds across every API instance and has no window edge where twice the limit could pass, as a per-minute counter does.

**Daily quota.** A user may ask `QUESTIONS_PER_DAY` (50) questions per UTC day, the user's choice; questions cost model calls, SQL submissions do not and only meet the rate limit. The question is taken from the quota when it is submitted, in one Lua script, so two requests at once cannot both take the last one, and is given back if it could not be queued (`TOO_MANY_JOBS`, or Redis failing). A question that is later ambiguous, unanswerable, or fails still counts: the model was called. Past the quota the API answers 429 `QUOTA_EXCEEDED` with `Retry-After` set to midnight UTC. Keys are per day and expire a day after it.

**Order of checks.** Validation and ownership come first, then the rate limit, then the quota, so a malformed request or someone else's connection id never uses up an allowance.

**Sign-in limit.** Dev login, refresh, and the Google callback are limited to `AUTH_REQUESTS_PER_MINUTE` (20) per IP address, with the same sliding window, so one source cannot flood them: each call costs a database lookup, a call to Google, or a new user. It is not what stops guessing: the app has no passwords (Google checks them), dev login is off in production, and refresh tokens are 32 random bytes. Behind a proxy every request shares the proxy's address until Express is told to trust it; that is deployment work (Phase 12).

**When Redis is down.** Submissions fail closed: the limit check fails and the request answers 500, as the queue needs Redis anyway. The sign-in limit fails open, the user's choice: the request goes through and a warning is logged, so a Redis outage does not also stop people signing in. The cost is that one address could flood sign-in during the outage.

**Usage.** The worker adds each finished job to `usage_counters` (one row per user and UTC day: questions, rows returned, input and output tokens), counted on the day the job was submitted. The table is apart from history so deleting history does not erase usage; it goes with the account. `GET /v1/usage` shows today's questions against the quota (the Redis count, which includes questions still running), the per-minute limit, finished questions, rows, and tokens. A job that crashes after recording and is retried can be counted twice; this is rare and only inflates the user's own numbers.

**Audit.** SQL the guard refused for good is audited as `query.rejected` with the job, connection, kind, and guard code, never the SQL, since a run of them can mean someone is probing the guard. Deleting one history entry (`history.deleted`) or all (`history.cleared`, with the count) is audited too, in the same database transaction as the delete, so there is never a delete without its audit row or an audit row for a delete that did not happen (the user's choice).
