# Request flow: asking a question

This page follows one question, "How many orders does each region have?", from the button in the browser to the customer's database and back. Every step names the file and the function, so you can open them side by side.

Checked against the code on 2026-10-18. If a path here no longer exists, the code is right and this page is out of date.

## The big picture

Four separate programs take part, and they talk only in the ways the arrows show:

```text
 Browser (apps/web)             API (apps/api)                Redis
 ──────────────────             ──────────────                ─────
 AskPage ─ POST /questions ───▶ JobsController.ask ─ add ───▶ queue "ayd-jobs"
         ◀── 202 + job ───────                                   │
                                                                 ▼ takes the job
 watchJob ─ GET /jobs/:id/events ▶ streamJob ◀─ job events ── Worker (apps/worker)
         ◀── SSE: job views ─────                               │
                                                                 ├─▶ Gemini (writes the SQL)
                                                                 ├─▶ SQL guard (checks it)
                                                                 ├─▶ customer database (read only)
                                                                 └─▶ app database (history, usage)
```

Three rules explain most of the design:

1. **The API never opens a customer's database and never calls the model.** It checks who you are and what you may do, queues a job, and answers at once. Slow or risky work happens in the worker.
2. **The model never sees anything the owner did not allow.** It gets only the allowlisted tables and columns, and it gets result rows only when the connection allows it.
3. **Nothing the model writes runs without the SQL guard.** The guard parses the SQL with PostgreSQL's own parser and rewrites it before it runs.

## Step by step

### 1. The browser sends the question

|                  |                                                                                                                                                                                                                                                                           |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Where**        | `apps/web/src/features/ask/AskPage.tsx`, `submit()`                                                                                                                                                                                                                       |
| **In**           | The text box contents and the selected connection id                                                                                                                                                                                                                      |
| **What happens** | The page checks the length (2,000 characters for a question), then calls `job.run(...)` from `useJobRunner()` (`lib/use-job-runner.ts`). That calls `askQuestion()` in `features/ask/api.ts`, then `runJob()` in `lib/jobs.ts`, then `api.post()` in `lib/api-client.ts`. |
| **Out**          | `POST /v1/connections/:id/questions` with body `{ "question": "..." }` and header `Authorization: Bearer <access token>`                                                                                                                                                  |
| **If it fails**  | A 401 makes `api-client.ts` refresh the token once and repeat the request. Any other error becomes an `ApiError`, which `useJobRunner` returns as `{ ok: false, error }`, and `FailureView` shows it.                                                                     |

The access token lives only in memory (`features/auth/AuthProvider.tsx`). The refresh token is in an HTTP-only cookie that page scripts cannot read (ADR 0014).

### 2. The API checks the request and queues a job

|                  |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Where**        | `apps/api/src/jobs/jobs.controller.ts`, `JobsController.ask()`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **In**           | The HTTP request                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **What happens** | (a) `AuthGuard` (`auth/protect-routes/auth.guard.ts`) verifies the token and puts the user on the request. (b) The global `ValidationPipe` (`common/validation.ts`) checks the body against `AskQuestionDto` (`jobs.dto.ts`) and trims the question. (c) `connections.get()` checks that the connection is yours. (d) `SubmissionLimits` (`limits/submission-limits.ts`) checks 10 submissions a minute, then takes one of your 50 questions a day. (e) `JobQueue.add('question.ask', ...)` (`packages/core/src/jobs/job-queue.service.ts`) claims one of your 3 job slots and puts the job on the BullMQ queue in Redis. |
| **Out**          | HTTP 202 with the job: `{ id, kind: "question.ask", state: "queued", ... }`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **If it fails**  | No token is a 401 `UNAUTHENTICATED`. A bad body is a 400 `VALIDATION_ERROR`. Someone else's connection is a 404 `NOT_FOUND`. Too fast or too many is a 429 `RATE_LIMITED`, `QUOTA_EXCEEDED`, or `TOO_MANY_JOBS`. A question that could not be queued is given back to the daily quota. Every error leaves through `AllExceptionsFilter` as `{ error: { code, message, requestId } }`.                                                                                                                                                                                                                                     |

### 3. The browser starts following the job

|                  |                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Where**        | `apps/web/src/lib/jobs.ts`, `watchJob()`; on the server, `apps/api/src/jobs/job-stream.ts`, `streamJob()`                                                                                                                                                                                                                                                                                                                      |
| **In**           | The job id from step 2                                                                                                                                                                                                                                                                                                                                                                                                         |
| **What happens** | The browser opens `GET /v1/jobs/:id/events` with `fetch`. `EventSource` cannot send the `Authorization` header, so `fetch` is used. The API keeps that response open as Server-Sent Events. It sends the job as it is now, then subscribes to the job's events (`JobEvents`, `packages/core/src/jobs/job-events.ts`, which listens to BullMQ through Redis). Each event makes it read the job again and send it if it changed. |
| **Out**          | A stream of `event: job` lines, each holding the full job view, including the current `stage`                                                                                                                                                                                                                                                                                                                                  |
| **If it fails**  | If the stream drops or is silent for 45 s, `watchJob` reconnects up to 3 times, then polls `GET /v1/jobs/:id`. Leaving the page aborts it.                                                                                                                                                                                                                                                                                     |

While the job runs, each update calls `onUpdate`. That sets `progress` in `useJobRunner`, and `JobProgress` (`components/JobProgress.tsx`) shows the stage.

### 4. The worker takes the job

|                  |                                                                                                                                                                                                                                                                                                                                               |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Where**        | `apps/worker/src/jobs/job-worker.ts` starts `startJobWorker()` from `packages/core/src/jobs/job-worker.ts`. That calls `JobProcessor.handle()` in `packages/core/src/jobs/job-processor.ts`.                                                                                                                                                  |
| **In**           | The BullMQ job: `{ name: "question.ask", data: { userId, connectionId, question } }`                                                                                                                                                                                                                                                          |
| **What happens** | The worker runs up to 5 jobs at once (`WORKER_CONCURRENCY`). A job cancelled while it waited ends at once. Otherwise `process()` sends it to the runner for its kind, here `AskJobRunner`. It passes a `JobContext` with `report(stage)`, which saves the stage as BullMQ progress so step 3 sees it, and an abort `signal` for cancellation. |
| **If it fails**  | An expected failure is an outcome (`{ ok: false, error }`), not a crash. Only an unexpected exception is retried, up to 3 times.                                                                                                                                                                                                              |

### 5. The question becomes SQL

|                  |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Where**        | `packages/core/src/ask/ask-job.runner.ts`, `AskJobRunner.run()` and `answer()`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **What happens** | (a) Stage `loading_schema`: `SchemaService.schema()` returns only the allowed tables and columns. (b) `selectTables()` (`ask/prompt.ts`) picks the tables that fit the prompt budget, those most like the question first. (c) `nextProposal()` uses a cached proposal for the same question and schema fingerprint if there is one (`ask/proposal-cache.repository.ts`, stored by `ask/sequelize-proposal-cache.repository.ts`). Otherwise, at stage `generating_sql`, `propose()` asks `LlmClient.generateObject()` (`llm/llm-client.ts`). That calls Gemini through `GeminiProvider` (`llm/gemini.provider.ts`) and falls back to a second model on failure. The answer must match `SqlProposalSchema` (`ask/sql-proposal.ts`). |
| **Out**          | A proposal: `{ status: "ok" \| "ambiguous" \| "unanswerable", sql, assumptions, clarifyingQuestion, explanation }`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **If it fails**  | "ambiguous" or "unanswerable" ends here with that result, and nothing runs. A model that is down or not configured ends with `LLM_UNAVAILABLE` or `LLM_NOT_CONFIGURED`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

### 6. The SQL guard checks the SQL

|                  |                                                                                                                                                                                                                                                                                                                       |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Where**        | `packages/core/src/sql-guard/sql-guard.service.ts`, `SqlGuardService.check()`. It calls `packages/sql-guard/src/guard.ts`, with the rules in `analyzer.ts`.                                                                                                                                                           |
| **What happens** | Stage `checking_sql`. The guard parses the SQL with PostgreSQL's parser. It accepts one `SELECT` that reads only allowed tables and columns, with approved functions and operators. It rewrites the SQL with schema-qualified names, `*` expanded, and `LIMIT` capped at 1,000 rows plus one. It never runs anything. |
| **Out**          | `{ allowed: true, sql }` with the rewritten SQL, or `{ allowed: false, code, reason }`                                                                                                                                                                                                                                |
| **If it fails**  | `onGuardRejected()` sends the SQL and the guard's reason back to the model, at most twice, then ends with `SQL_REJECTED`. A cached proposal the guard now refuses is dropped, and the model is asked instead.                                                                                                         |

### 7. The SQL runs on the customer's database

|                  |                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Where**        | `packages/core/src/jobs/run-checked-sql.ts`, `runCheckedSql()`. It calls `ConnectionService.resolveTarget()` (`connections/connection.service.ts`) and `QueryExecutor.run()` (`user-database/query-executor.ts`).                                                                                                                                                                                                                                              |
| **What happens** | Stage `connecting`: `resolveTarget()` checks ownership, decrypts the login in memory (`@ayd/crypto`), and resolves the host. The SSRF guard (`@ayd/ssrf-guard`) checks every address it resolved to. Stage `running_query`: the executor takes one of the connection's 2 slots in Redis. It opens a `READ ONLY` transaction with a 15 s statement timeout and an empty `search_path`, and reads through a cursor up to 1,000 rows or 5 MB. Then it rolls back. |
| **Out**          | `{ ok: true, columns, rows, rowCount, truncated, durationMs }`, or a failure with a code                                                                                                                                                                                                                                                                                                                                                                       |
| **If it fails**  | `onQueryFailed()` decides. An invalid query gets one rewrite from the model. A table or column the database no longer has (`QUERY_SCHEMA_CHANGED`) makes `run()` refresh the schema and answer once more. A timeout, a permission error, or a lost connection is final.                                                                                                                                                                                        |

### 8. The answer is built

|                  |                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Where**        | `AskJobRunner.buildAnswer()`                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **What happens** | The proposal is saved to the cache. `computeFacts()` (`ask/facts.ts`) works out totals on the server. `selectChart()` (`ask/chart.ts`) picks stat, line, bar, pie, or table from fixed rules. At stage `summarizing`, `summarize()` asks a lighter model for two or three sentences, and keeps them only if every number in them appears in the data. Otherwise a template from the facts is used. Rows go to that model only if the connection allows it. |
| **Out**          | `{ ok: true, result: { status: "answered", sql, rows, chart, facts, summary, usage, ... } }`                                                                                                                                                                                                                                                                                                                                                               |

### 9. The worker records the outcome

|                  |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Where**        | `JobProcessor.finish()` and `record()`                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **What happens** | `historyEntryFor()` (`history/query-history.repository.ts`) builds a history row: the question, the SQL, the status, and the token counts, but never the rows. It is written to the app database. Today's usage counters are increased (`limits/sequelize-usage-counters.repository.ts`). SQL the guard refused for good also writes a `query.rejected` audit row. BullMQ stores the outcome in Redis for 15 minutes and fires `completed`. When the job ends, the worker releases its user slot. |

### 10. The answer reaches the screen

|                  |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Where**        | `streamJob()` in the API, then `watchJob()`, `useJobRunner()`, and `AskPage` in the browser                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **What happens** | `completed` reaches `JobEvents`. `streamJob` reads the finished job, sends it, and closes the stream. `watchJob` sees a finished state and returns. `useJobRunner` turns the view into `{ ok: true, result }` and clears the progress. `AskPage` stores the outcome. `AnswerView` (`features/ask/components/AnswerView.tsx`) shows the summary, the chart (`ResultChart`, loaded only when needed), the table (`ResultTable`), and the SQL with its assumptions. The page also refreshes history and usage. |

## Other paths that reuse these steps

- **Run your own SQL** (`POST /v1/connections/:id/queries`, a `query.run` job): steps 1 to 4, then `QueryJobRunner` (`jobs/query-job.runner.ts`) does steps 6, 7, and 9. There is no model and no summary.
- **Run again from history** (`POST /v1/history/:id/rerun`): replays the stored SQL as a `query.run` job, with no model call.
- **Connect, test, or read a schema**: the same queue and stream, with `ConnectionJobRunner` (`jobs/connection-job.runner.ts`) in the worker.
- **Cancel** (`POST /v1/jobs/:id/cancel`): the API publishes the job id on a Redis channel (`jobs/job-cancellation.ts`). The worker aborts that job's signal, and the job ends as `cancelled` at its next stage.
